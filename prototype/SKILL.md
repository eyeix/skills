# 原型

原型是**回答一个问题的抛弃型代码**。问题决定形状。

## 选分支

用用户的提示、上下文代码判断要回答哪个问题,用户在场拿不准就问:

- **"这个逻辑 / 状态模型对不对?"** → 读 [LOGIC.md](LOGIC.md)。产出单个可分享的 HTML 文件(自由按钮 + 分页引导场景),把状态机推过那些纸上难推理的案例,非开发者也能上手;
- **"这该长什么样?"** → 读 [UI.md](UI.md)。在同一路由上生成多个截然不同的 UI 变体,URL 参数切换,底部浮动条选择。

两个分支的产物完全不同,选错就白做。问题真模糊且用户不在场时,按上下文代码选更贴合的一支(后端模块 → 逻辑;页面或组件 → UI),并在原型顶部声明这个假设。

## 两个分支共同的规则

1. **从第一天起就是抛弃型的,并明确标记**。原型代码放在它真正服务的位置旁(被原型化的模块或页面边上),上下文一目了然;命名让随便哪个读者一眼看出它是原型,不是产品。抛弃型 UI 路由遵守项目既有路由约定,不发明新的顶层结构;
2. **一条命令可运行**。UI 原型从项目任务器一条命令启动(`pnpm <name>`、`python <path>`、`bun <path>` 等);逻辑演示是双击即开的单个 HTML。启动不需要思考;
3. **默认不持久化**。状态在内存里。持久化是原型要**检验**的东西,不是它依赖的东西。问题真涉及数据库时,用 scratch 库或明确标注 "PROTOTYPE, 可删" 的本地文件;
4. **跳过打磨**。不写测试,不做超出"能运行"的错误处理,不建抽象。目的是快速学到东西;
5. **暴露状态**。每次操作后(逻辑)或每次变体切换时(UI),打印或渲染完整的相关状态,让用户看见什么变了;
6. **完成后捕获**。验证过的决策折进真实代码,原型本身作为**一手来源**捕获:提交到 main 之外的抛弃型分支(`prototype/<名字>`),在任务文档或工单上留下指向该分支的上下文指针。答案本身(结论与它解决的问题)也记进工单或 commit。main 只保留验证过的决策。
