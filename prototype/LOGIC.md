# 逻辑原型

单个自包含 HTML 文件(一份**可分享的演示**),让人靠点按钮驱动一个状态模型。问题关于**业务逻辑、状态流转或数据形状**时用它:那种纸上看着合理、推过真实案例才发现不对的东西。

因为是一个文件、零安装,可以把它交给非开发者(设计师、产品、领域专家),让他们自己感受这个模型。所以它说他们的语言,不说代码的语言。

## 什么时候选这个形状

- "不确定这个状态机能不能处理 X 之后 Y 的边界情况。"
- "这个数据模型到底能不能表达……的情况?"
- "想在写 API 之前先摸清它该长什么样。"
- 任何想**按按钮、看状态变**的场景。

问题是"这该长什么样"时选错了分支,改用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码前,写下原型的是什么状态模型、回答什么问题。一段话,放在演示顶部(可见的简介,不只是注释)。回答错的问题的逻辑原型是纯浪费,把问题写明白,事后可核对——无论用户现在看着,还是之后回来看。

### 2. 把逻辑隔离成可移植模块

真正的逻辑(回答问题的那部分)放单个 `<script>` 块,写成一个小而纯的模块,日后能整个拎出放进真实代码库。页面外壳是抛弃的,这个模块不是。

形状跟着问题走:

- **纯 reducer**:`(state, action) => state`。动作是离散事件、状态是单值时适用;
- **状态机**:显式的状态与迁移。"现在哪些动作合法"本身是问题的一部分时适用;
- **一组纯函数**,作用于一个普通数据类型。没有隐式的当前状态、只有变换时适用;
- **方法面清晰的类或模块**,当逻辑确实持有持续的内部状态时。

选最贴合问题的形状,不是最易接线的形状。保持纯:不碰 DOM、不碰 `document`、按钮处理器不伸进来。页面调它,不反向。这让原型活得比它自己久:问题一答完,验证过的 reducer / 状态机 / 函数组就独立搬进真实模块。

### 3. 搭可分享的 HTML 文件

一个文件,纯 HTML/CSS/JS:无框架、无打包器、无服务器,全部内联,双击可开,发邮件也不坏。任何人打开就能跑。

为非开发者写。每个标签用**领域语言**,不用代码:按钮与状态读起来像业务,不像 reducer。用平实的词解释正在发生什么。

自上而下干净分层:

1. **标题与一句话说明**:这个演示让你探索什么(第 1 步的问题);
2. **当前状态**:完整的相关状态渲染成可读面板(带标签的字段,不是裸 JSON),每次点击后重渲染,让变化可见。有助于非开发者跟上的地方,点明刚刚变了什么;
3. **自由按钮**:每个动作一个按钮,始终可用,任何人能以任意顺序戳这个模型。每次点击派发动作并重渲染;
4. **引导场景**:一组**场景**,每 tab 一个。每个 tab 一段平实的话描述场景(它摆的局面、该注意什么),下面是该场景依次要按的**按钮**。每步是真按钮:点击执行该动作并进入下一步。进入引导时重置到已知的初始状态,场景每次跑得一样。

挑尴尬的场景:正常路径、一个刁钻边界、一次应该被拒绝的尝试。

克制地做美:干净的排版、充裕的留白、一个强调色。无动画、无花活:不跟状态和按钮抢注意力。

### 4. 交付

把文件发给对方,或帮他们打开。他们有空时自己点;有价值的时刻是他们说"等等,这不该可能"或"咦,我以为 X 会不一样"——那是**想法里的 bug**,正是全部意义。他们要新动作或新场景,就加。原型会进化。

### 5. 捕获答案与原型

原型答完问题,捕获答案,再按 [SKILL](SKILL.md) 第 6 条的方式捕获原型。逻辑分支的对应关系:验证过的 reducer / 状态机 / 函数组搬进真实模块(决策,吸收);HTML 外壳随抛弃型分支保存为原型一手来源——自包含单文件,在那儿永远可复跑。

## 反模式

- **不写测试。**需要测试的原型不再是原型;
- **不接真实数据库。**内存状态,除非问题恰好关于持久化;
- **不做泛化。**没有"万一以后要支持 X"。原型只回答一个问题;
- **不把逻辑和页面糊在一起。**纯模块引用了 DOM、`document` 或按钮处理器,就拎不出来了。页面是纯模块外面的薄壳;
- **不上框架、打包器、服务器。**一个收件人双击就开的文件;React 应用或 dev server 毁掉"可分享";
- **不把 HTML 外壳发上生产。**页面是为手点优化的,后面那个逻辑模块才值得留下。
