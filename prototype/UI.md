# UI 原型

在同一路由上生成**多个截然不同的 UI 变体**,底部浮动条切换。用户在浏览器里翻看,挑一个(或从每个里偷一点),其余扔掉。

问题关于逻辑/状态而非长相时选错了分支,改用 [LOGIC.md](LOGIC.md)。

## 什么时候选这个形状

- "这个页面该长什么样?"
- "定稿前想看看这个仪表盘的几个方案。"
- "给设置页换个布局试试。"
- 任何用户原本要在脑中三张模糊草图之间耗一天的时刻。

## 两个子形状:强烈优先 A

UI 原型在与应用其余部分**贴着比**时好判断得多:真实的头部、真实的侧栏、真实的数据、真实的信息密度。孤立的一条抛弃路由是真空:每个变体单看都不错。有可依托的既有页面时默认子形状 A;原型确实无处安放才用 B。

### 子形状 A:在既有页面上调整(首选)

路由已存在。变体渲染在**同一路由**上,由 `?variant=` URL 参数门控。既有的数据获取、参数、鉴权全部保留,只换渲染层。这是默认,没有具体理由就不偏离。

原型化的东西还没有页面、但**天然住在某个页面里**(仪表盘的新区块、设置页的新卡片、流程里的新步骤),仍是子形状 A:把变体挂进宿主页面。

### 子形状 B:新页面(最后手段)

只用于原型化的东西确实没有可依附的既有页面(全新的顶层界面,或嵌不进任何合理位置的流程)。

按项目既有路由约定建**抛弃路由**,不发明新的顶层结构,命名一眼可见是原型(路径或文件名含 `prototype`)。同样的 `?variant=` 模式。

选 B 之前自查:真的没有页面能嵌吗?空路由会藏住有内容的路由会暴露的设计问题。

两个子形状的底部浮动条完全相同。

## 流程

### 1. 陈述问题并定数量

默认 **3 个变体**。超过 5 个就不再是截然不同,而是噪音,以 5 为上限。

把计划写成一 行,放在原型位置或文件顶部注释:

> "设置页三个变体,经 `?variant=` 切换,挂在既有 `/settings` 路由上。"

用户在与不在,这一行都有效。

### 2. 生成截然不同的变体

逐个起草,每个都要:

- 服从页面用途与它可访问的数据;
- 用项目的组件库 / 样式体系(TailwindCSS、shadcn、MUI、纯 CSS,是什么用什么);
- 有清晰的导出组件名,如 `VariantA`、`VariantB`、`VariantC`。

### 3. 接线

在路由上建一个统一的切换器:

```tsx
// 伪代码,适配项目框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形状 A(既有页面):既有的数据获取全部留在切换器之上,每个变体只换渲染的子树。

子形状 B(新页面):`/prototype/<name>` 抛弃路由挂同一个切换器。

### 4. 建浮动切换条

屏幕底部居中一条小的固定定位栏,三件套:

- **左箭头**:切到上一个变体(循环);
- **变体标签**:当前变体 key,变体有导出名就带上,如 `B (侧栏布局)`;
- **右箭头**:切下一个(循环)。

行为:

- 点箭头更新 URL 查询参数(用框架路由,如 Next 的 `router.replace`、React Router 的 `navigate`),变体可分享、刷新不丢;
- 键盘 `←` `→` 也能切;`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不拦截;
- 视觉上与页面明确区分(高对比胶囊、轻投影),一眼看出它不是被评审设计的一部分;
- 生产构建里隐藏:以 `process.env.NODE_ENV !== 'production'` 或等价检查门控,避免原型误合并把切换条发给用户。

切换器放进单个共享组件,两个子形状复用。位置在项目放共享 UI 的地方。

### 5. 交付

给出 URL(与 `?variant=` 各键)。用户有空时自己翻。有价值的反馈通常是**"我要 B 的头部配 C 的侧栏"**——那才是他们真正想要的设计。

### 6. 捕获答案并清理

变体胜出后,捕获答案(哪个变体、为什么),再按 [SKILL](SKILL.md) 第 6 条的方式捕获原型。胜者折进真实代码,其余移上抛弃分支,不进 main:

- **子形状 A**:胜者折进既有页面;main 上删掉落选变体与切换器;
- **子形状 B**:胜者升级为正式路由;main 上删掉抛弃路由与切换器。

全部变体是一手来源,落在抛弃分支而不是垃圾桶:留在 main 的变体组件与切换器烂得快,还困惑下一个读者。

## 反模式

- **只差颜色或文案的变体。**那是微调,不是原型。真变体在结构上意见相左;
- **变体间共享太多代码。**共享一个 `<Header>` 可以;共享 `<Layout>` 就输了。每个变体都要能自由推翻布局;
- **变体接真实写操作。**只读原型没问题。变体需要写时指向 stub:问题是"该长什么样",不是"后端能不能用";
- **把原型直接晋升生产。**变体代码是在原型约束下写的(无测试、最少错误处理)。折进去时正经重写。
