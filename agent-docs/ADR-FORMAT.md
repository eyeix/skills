# 决策记录格式

决策记录位于 `.agentdocs/adr/`,文件名 `NNNN-kebab-slug.md`,编号从 `0001` 递增。首次需要记录决策时创建该目录。

## 三条门槛

全部满足才记录,任何一条不满足则跳过:

1. **难逆转**:事后改主意的成本显著;
2. **无上下文会困惑**:未来读者会问"当时为什么这样做";
3. **真实权衡**:存在真实的备选方案,且为特定理由选定了其一。

易逆转的决策记了也会被直接推翻;不令人意外的决策没人会问;没有备选的决策只是"做了显然的事"。

## 模板

```markdown
# <决策标题>

<一到三句:什么背景下,决定了什么,为什么>
```

到此为止。决策记录的价值在于记录"做了这个决定"与"为什么",不在于填满章节。

## 可选章节

只在真正增加信息时包含:

- **备选方案**:被否决的选项值得记住时;
- **后果**:不明显的下游影响需要点明时;
- **状态**:决策被重新审视时,在文件开头注明被 `NNNN` 取代或标记废弃。

## 编号

扫描 `adr/` 取当前最大编号,加一。

## 典型适格决策

- 架构形态:事件溯源写模型、读模型投影到 Postgres;
- 上下文间集成方式:领域事件,非同步 HTTP;
- 带锁定的技术选型:数据库、消息总线、认证提供方,即换掉需要一个季度以上的那种,普通依赖库不算;
- 边界与归属:客户数据只由客户上下文持有,其他上下文只持 ID 引用。明确的"不"与"是"同样值得记录;
- 对显然路径的刻意偏离:手写 SQL 而非 ORM,因为 X。记录它,防止后来者把刻意为之当成缺陷修复;
- 代码中不可见的约束:合规要求禁止某云厂商、合作方契约要求 200ms 内响应。
